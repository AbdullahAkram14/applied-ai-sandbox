## Plan from chat

Feature: Note Search

Data model:

* No note dictionary changes are needed.
* Existing notes already have `title` and `body`, which are enough for searching.

Route changes:

* Update the home route (`/`) to read an optional query parameter called `q`.
* If `q` is empty or missing, show all notes.
* If `q` has text, filter notes where the title or body contains the search term.
* Search should be case-insensitive.

UI changes:

* Add a small search form near the top of the notes list.
* The form should use `method="GET"` and submit to `/`.
* The input should be named `q`.
* Preserve the current search text in the input field after submission.

Edge cases:

* Empty search should show all notes.
* Search should work for title matches.
* Search should work for body matches.
* Search should not crash when there are no notes.
* Search should show zero matching notes if nothing matches.

Acceptance criteria:

* Searching by title filters matching notes.
* Searching by body filters matching notes.
* Empty search shows all notes.
* Existing note creation still works.

## Workflow Retro

For this feature, I used all four workflow lanes. I started with chat to plan the note search feature before writing any code. The planning step helped me think through the data model, route changes, UI updates, and edge cases without immediately jumping into implementation. After that, I used Claude Code to execute the feature by updating the home route, adding a search form, and creating tests for the new behavior.

I used Copilot for small polish tasks rather than larger implementation work. It was useful for quick edits and cleanup because it did not require writing a detailed prompt or waiting for a full agent cycle. For larger changes, Claude Code was more effective because it could understand the project structure and modify multiple files together.

The review stage showed the value of using a separate tool. Looking at the work from a different perspective helped confirm that case-insensitive searches and empty-search behavior were covered. Even when the feedback did not require major code changes, it served as a useful verification checkpoint.

I also experimented with parallel work using a second Claude Code session in a separate worktree. The second task was small, so one session mostly sat idle, but the exercise showed how multiple agents could be useful when working on larger features with independent tasks.

If I repeated this workflow, I would spend more time refining the planning stage before implementation. The conductor role—checking plans, verifying outputs, and deciding which tool to use—ended up being more important than writing the code itself.
